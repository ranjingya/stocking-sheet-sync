# 老款数仓预测试算

## 使用方式

试算命令直接读取本项目配置的数仓。`--snapshot` 按需求表快照中的SKU查询，范围与服务填充一致；`--style` 用于按款号读取全部SKU的独立诊断。输出本地计算证据。它不访问飞书、不写Redis、不创建文件副本、不发送通知，也不受服务填充开关控制。

```bash
uv run stocking-sheet-sync-forecast \
  --style KQ25073 \
  --as-of 2026-09-12 \
  --output artifacts/forecast-trial
```

需求表范围试算使用 `--snapshot artifacts/表格目录/sheet-snapshot.json`，与 `--style` 二选一。多个款式可重复传入 `--style`。日期必须显式指定。配置分别为：

- `.env` 的 `WAREHOUSE_*`：数仓连接。
- `config/sales-sources.toml`：平台出库明细来源和筛选。
- `config/forecast-sources.toml`：整款主数据、京东每日快照及全公司来源状态。
- `config/forecast.toml`：季节和需求分配规则。
- `config/sheet-layout.toml`：款式年份分类规则。

输出 `forecast.json` 保存主数据、窗口、逐平台来源结果、异常及分配过程；`forecast.csv` 保存逐SKU的当前30天、去年同期30天、去年后续周期、占比、取整和最终试算量。错误项的预估为空。返回码0表示全部可计算，2表示报告中有待核对项，1表示运行或配置失败。

`ready` 表示该平台整款试算通过当前校验，不代表目标表可以直接写入。表内商品身份、人工值和公式保护属于写入阶段的独立检查。

## 数据校验

商品主数据按所选查询范围投影去重，保留SKU、款号、名称、规格和标签。相同SKU出现不同身份或标签、请求的不同款式共享SKU、季节冲突时，该款暂停计算。需求表模式仅查询表内SKU，并按这些SKU分款汇总、分配。按款号模式用于诊断该款全部主数据SKU。

拼多多、唯品、京东POP、猫超沿用销售出库明细筛选和业务主键去重，并分别检查三段历史窗口逐日覆盖。在整个平台窗口均有出库记录且主数据有效的前提下，SKU无出库记录按零处理。每日存在记录只能证明日期有数据，不能证明上游同步在日内绝对完整。

京东自营以 `dt` 为业务日。固定7、14、28、30、60、90天读取截止日相应滚动字段，仅要求截止日记录唯一、SKU标识完整、数量有效。其他1至366天区间累加 `outbound_yesterday`，逐SKU每天必须恰有一条有效记录。缺日、重复或非法数量需要核对；固定周期与日累计的差异不作为失败条件。

全公司占比兜底读取需求表前部的去年生命周期销量，保留周期原文。触发条件为表内同款SKU少于10且该平台当前30天合计少于20；只替换SKU分配占比，平台总需求公式保持不变。`--style` 未提供需求表，公司兜底不可用时返回人工判断。

## 结果状态

- `ready`：可计算，仍需通过目标已有内容保护检查才能写入。
- `manual`：去年同期为零，或触发兜底但公司销量缺失、歧义、不完整、合计为零。预估留空并记录原因，已有值保留。
- `needs_review`：商品身份、季节、来源记录或计算异常。服务填充按失败降级处理。

三个状态均保留可取得的历史输入。人工判断项允许其他可计算项写入。CLI返回码2提示报告存在人工判断或待核对项；0表示全部可计算，1表示运行或配置失败。
