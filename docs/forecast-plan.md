# 老款需求预测实施计划

## 已确认规则

- 首版只计算老款通用预测，新品保留历史数据供人工填写。
- 当前观察窗口为预估日前30个完整自然日，按发货件数统计。
- 去年同期观察窗口为去年对应预估日前30天；去年后续窗口为预估日往前一年至预测截止日往前一年，包含末日。
- 商品季节读取 `std_api_jstbz_product_spec_info_f.labels`，按逗号拆分：夏款到当年8月31日，秋冬款到本销售季1月31日；四季款和标签缺失取下单日当天或之后最近的1月31日或8月31日。秋冬款1月下单截至当年1月31日，其余正常冬季下单截至次年1月31日。
- 跨季夏冬款不纳入首版自动处理；出现截止日早于预估日时标记待核对，不自动延长一年。
- 各平台分别按款式计算：去年后续周期量 × 今年近30天量 ÷ 去年同期近30天量。
- SKU占比默认采用本平台该款今年近30天销量。整款SKU数少于10且平台整款近30天销量少于20时，采用全公司该款近30天SKU占比。兜底只替换占比，不替换平台需求总量。
- 款式总量按 SOP 向上取整到件，SKU默认四舍五入到件（0.5向上），差额优先调整到占比最高的SKU；并列按SKU编码排序，调整后非负且合计等于款式总量。
- 去年同期为零、历史数据不完整、全公司兜底无有效分母时，预估留空并记录原因；不自动加1。
- 预测不扣库存和采购在途。拼多多实退暂不处理。
- 系统预估与人工需求分列，原人工需求、公式及历史字段保留。

## 表格目标

市场部增加“全公司近30天”列。老款每个平台有五项：今年近30天、去年同期近30天、去年对应后续周期、AI预估、人工需求。近30天现有列复用；已存在的其他历史指标保留，不能将日期不同的历史列当成同一指标。

## 实施步骤

1. **规则模块与外部配置**：实现季节识别、时间窗口、同比计算、占比兜底、取整与合计校验。补充边界测试，独立提交。
2. **数据读取与本地试算**：读取整款SKU和标签；扩展指定历史区间查询；核验京东自营日出库的日期归属和重复维度；确定全公司统计覆盖与去重，避免ERP向自营仓调拨与自营终端销量重复相加。输出计算依据、来源状态、日期和逐SKU结果。
3. **表格结构与填充**：补齐全公司和各平台新增字段，定位原人工需求列。历史开关控制历史列写入，预测开关控制预估列写入；预测可以读取历史作为输入。无法计算的项留空，保持现有失败降级交付策略。
4. **测试副本验收**：使用真实老款验证日期窗口、数据来源、SKU分配、原内容保护、重复执行及强制重搬。核验完成后提交，不推送、不部署。

## 数据质量与待核验事项

这些属于技术核验，不替代已确认的业务规则：

- 同SKU历史记录及同款各SKU季节标签是否一致；多季节冲突进入待核对，不任意取一个。
- 标签缺失按四季；仅包含非季节标签也按季节缺失处理。
- 整款SKU应来自主数据，目标表缺SKU时报告缺口，不能将整款总量分摊给部分SKU。
- 京东自营 `outbound_yesterday` 的业务日期映射，完整日覆盖和同日条码唯一性。
- 全公司出库范围、内部流转排除及终端销量是否包含自营，需从来源定义和真实数据核实。
- 闰日往前年份映射到2月28日；观察窗口始终保持30个自然日。
- 历史已过截止日、缺失日期及主数据冲突均提供原因，不使用未经验证的数值。

## 验收标准

规则测试覆盖三个季节与空标签、跨年与闰年、阈值边界、零分母、同比下降、取整正负差额、多个款式和平台隔离。数仓试算提供真实证据，表格验证保护人工需求、公式、样式及其他部门内容。尚未验证的数据来源不启用自动预测。
