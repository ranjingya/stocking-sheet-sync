# 市场部下单需求预测规则与实施计划

本文用于确定预测需求数量的业务口径和实现边界。规则来源为下单需求讨论记录、拼多多 SOP 和本项目已确认的填表要求。本文中的“建议”及“待确认”属于实施方案，不作为已启用的自动计算规则。

当前项目已支持新品近30天发货数据填充、三份副本搬运、失败降级和批次去重。预测尚未实现，`FILL_FORECAST_ENABLED=true` 时返回 `unsupported` 并降级交付原始备份。本文不改变运行配置。

## 1. 预测目标与填充范围

预测的是各平台从预估日到本季结束的预计发货需求，先计算款式总量，再分配到该款式各 SKU。该数量供运营审核调整。

首批对象为当前配置识别的 `KQ26` 开头新品。新老款规则由外部配置维护；老款公式在本文记录，老款所需历史窗口及表格支持另行实现。

| 平台 | 历史参考列 | 预测写入列 |
| --- | --- | --- |
| 唯品会 | 唯品近30天 | 唯品会 |
| 京东自营 | 自营近30天 | 京东自营 |
| 拼多多 | 拼多多近30天 | 拼多多 |
| 天猫超市 | 猫超近30天 | 天猫超市 |
| 京东 POP | 京东POP近30天 | 京东POP |

列位置通过市场部表头和配置别名定位，保留模板中的实际表头。POP 和猫超分别计算，不能合并为“市场部其他”。只填写市场部需求商品行，已有人工数量、公式、合计及其他部门内容保留。

历史销量是计算依据，不计入预测需求合计。会议确认库存由后续环节与需求比较，本阶段不扣现有库存。建议同样将采购在途留给后续采购缺口环节处理，不在预测公式中引入扣减；在途抵扣规则不属于本项目已确认的业务规则。

## 2. 统计口径与日期

### 已明确的口径

- 使用发货时间和已出库件数。拼多多 SOP 的支付件数口径，在本任务中采用已确认的发货口径。
- 当前观察窗口为预估日前30个完整自然日，不含预估日当天。
- 五个平台独立取数、计算和分配，不以全公司销量替代平台销量。
- 新品历史参考统一展示近30天。SOP 允许上架至今作为补充参考，当前自动规则不切换为近7天或上架至今。
- 冬季覆盖到次年1月或2月，夏季覆盖到8月；每次预测仍须明确准确截止日期。
- 去年参考的是与本次未来需求周期对应的后续销量，不是去年整个销售季的总销量。

### 日期参数

| 参数 | 含义 | 状态 |
| --- | --- | --- |
| 预估日 `D` | 当前观察窗口截止边界、未来需求起点 | 自动历史填充使用原始备份创建时的上海日期；预测建议沿用并冻结 |
| 需求截止日 `E` | 本次剩余销售周期最后一天 | 待按季节或任务明确 |
| 当前观察窗口 | `[D-30天, D)` | 已确定 |
| 去年观察窗口 | 与当前观察窗口对应的去年30天 | 需明确日历映射，以及活动、闰日偏差处理 |
| 去年后续窗口 | 与本次 `[D, E]` 对应的去年日期区间 | 随预测周期确定 |

建议第一版按日历日期映射去年同期，并保持观察窗口为30天；活动错位由运营复核。跨年周期按完整起止日期保存，查询统一使用左闭右开区间。不能将会议中的“26年2月”直接作为未来需求截止日：该处讨论的是历史参考周期。

## 3. 老款预测规则

按“平台＋款式”汇总：

- `A`：本款当前近30天发货量。
- `B`：本款去年同期30天发货量。
- `C`：本款去年对应后续需求周期发货量。

```text
同比增长率 = (A - B) / B
款式基础需求 = C × (1 + 同比增长率) = C × A / B
```

会议与 SOP 对此基本一致。同比下降时按下降比例计算，不默认沿用去年需求。

`B` 为零或缺失时不能计算同比；历史覆盖不完整时不能把缺失当成零。断货、活动、调价和投流等影响由运营复核，系统保留原始计算依据。

## 4. 新品参照款与预测规则

### 4.1 参照款筛选

会议明确的筛选顺序：同平台、同聚水潭虚拟分类、去年同季节时间段、同期销量规模接近。

SOP 进一步要求参考功能、价格带、目标人群和生命周期阶段；允许选择2—3个相似款，以中位数或较保守结果参考。这些条件需要数据字段和选择标准，不能直接认定当前数仓已经具备。

建议第一版先输出候选清单：参照款编码、名称、虚拟分类、去年同期销量、后续周期销量、与新品销量差异及数据覆盖。运营可明确指定参照款；自动选择应等以下规则确定后启用：

- 虚拟分类使用哪一级、同款多个分类如何处理。
- 销量相似度的计算方式和接受阈值。
- 多候选采用单款、多个系数的中位数，还是其他方式。
- 无符合条件的候选时留空，不自动退到跨平台或不同分类。

### 4.2 计算方式及来源差异

设 `N` 为新品当前近30天发货量，`R` 为参照老款去年同期30天发货量，`L` 为参照老款去年对应后续需求周期发货量。

| 来源 | 计算描述 |
| --- | --- |
| 会议 | 找到同期销量接近的老款，参考其后续周期销量 `L`，再人工取整 |
| 拼多多 SOP | 计算后续周期系数 `L / R`，新品基础需求为 `N × L / R` |

**建议第一版采用 SOP 比例公式，作为待确认方案。** 它可以解释新品与参照款的销量规模差异；其他平台是否统一采用该公式仍需确认。`N` 与 `R` 接近时，结果也接近直接使用 `L`。

SOP 的“同生命周期阶段”与会议的“去年同期”不必然一致。首版建议使用去年同期作为参照窗口，保留阶段差异供人工复核，不自动推断生命周期阶段。

`R` 必须大于零。缺少可靠参照、分类、有效窗口或完整历史数据时，预测留空并记录原因。新品平台近30天总量为零时无法建立可靠销量比例，建议转人工，不自动填零需求。

## 5. SKU 分配与取整

使用待预测款式自身在该平台的 SKU 发货占比：

```text
SKU占比 = 本SKU当前近30天发货量 / 本平台本款全部SKU当前近30天发货量
SKU基础需求 = 本平台款式基础需求 × SKU占比
```

款式汇总应覆盖该平台该款式的全部 SKU。若目标表只列部分 SKU，应列出缺失范围供核对，不能把整款需求全部分摊给表内部分 SKU。

### 取整规则需要统一

- 会议：SKU 以10为单位取整；款式总量出现人工向上取整示例，未规定统一粒度。
- SOP：款式需求按件向上取整；有整箱或起订量要求时再按相应规则向上取整；SKU 取整差额优先分配给销量占比最高的 SKU。

建议首版采用一个可确定执行的方案：款式总量向上取整到10的倍数，SKU 按占比分配后向下取整到10的倍数，剩余整十数量分配给占比最高的 SKU；占比相同时按 SKU 编码排序。该方案仍需业务确认，不将会议示例中的取整幅度写为固定规则。

验收条件为 SKU 数量非负、满足最终确定的取整粒度、SKU 合计等于款式最终需求量。零销量 SKU、断货 SKU、刚上架 SKU 需要单独标明；是否分配最低数量不设隐含默认值。

## 6. 数据准备与缺口

已有来源和平台筛选条件见 [历史发货数据读取与表格匹配](sales-data.md)。下表区分现有能力与预测新增需求。

| 数据 | 当前情况 | 预测实施前需完成 |
| --- | --- | --- |
| SKU、款式身份 | 使用 `std_api_jstbz_product_spec_info_f` 核对 | 核对整款全部 SKU 及历史编码变更 |
| 五平台当前近30天 | 已支持读取和填充 | 复用同一预估日、平台范围和质量检查 |
| 聚水潭虚拟分类 | 预测筛选尚未接入 | 确认数仓表、字段、分类层级及款式关联 |
| 季节、上市年度、价格与功能 | 未形成预测输入 | 确认可取字段，缺失项使用外部业务配置或人工补充 |
| POP、猫超、拼多多、唯品会去年同期及后续量 | 当前历史读取聚焦近30天 | 核对明细历史留存、平台归属、日期覆盖，增加指定历史区间查询 |
| 京东自营去年同期及后续量 | 当前用 BWD 日快照的 `outbound_30d` | 核实历史快照留存，并寻找可统计任意后续周期的出库明细或日粒度数据 |
| 断货、异常订单、活动、投流 | 未接入预测修正 | 首版保留人工复核入口及原因，不自动设置修正系数 |

京东自营的 `outbound_30d` 是滚动30天值，不能把连续日快照相加得到季节销量。当前能读取近30天，不代表已具备去年整段剩余周期的可靠统计能力。

逐日存在记录只是覆盖证据，不能证明 ETL 已完整同步。预测也应区分“数据缺失”与“观察窗口内确实无发货”，不能为得到结果自动缩短窗口或改用其他日期。

## 7. 试算输出与写入保护

先生成本地 JSON/CSV 试算明细，供人工核对，不增加结果查询页面或常驻查询服务。建议每项包含：

- 批次、预估日、需求截止日、规则版本及取数时间。
- 平台、款式、SKU、目标单元格和原值。
- 当前30天量、去年同期量、去年后续量及各自窗口。
- 参照款及筛选依据、采用公式、款式基础需求与取整后需求。
- SKU 占比、取整前后数量、差额分配过程。
- 可填写状态、异常原因和是否需要人工复核。

只有依据齐全、规则明确、目标单元格为空的需求才列为可写；已有相同值可跳过，已有不同人工值或公式保留并列出冲突。计算明细保存在本地报告，不增加未经约定的表格列，不改现有合计公式。

只开预测开关时仍可能需要读取历史数据作为计算输入；“是否填历史数据”控制历史列写入，不应被解释为预测不能读取历史。这是预测实现需要支持的行为，当前仅开启预测的运行流程尚不具备此能力。

## 8. 异常与搬运流程

| 情况 | 预测阶段处理原则 |
| --- | --- |
| 分类或参照缺失、分母为零、日期缺口 | 不生成该项可写数量，记录原因供人工处理 |
| 去年断货、异常销量、生命周期差异 | 展示风险依据，由运营调整 |
| 非空需求冲突或公式单元格 | 保留原内容，记录冲突 |
| API、写入或核验失败 | 保留处理备份与执行记录，遵循失败降级流程 |

现有搬运流程在启用的填充阶段失败时交付原始备份，处理备份保留供核验。预测部分 SKU 留空是否属于“允许交付的部分完成”，需要明确；在明确前，不能把存在阻塞项的预测当作全部填充成功。

所有写入在处理备份上执行。交付决定冻结后，同批次重试不重新计算；需要更换参照款、日期或规则重新计算时，通过手动命令创建新批次。

## 9. 实施顺序与验收

1. **确认规则和数据**：确定预测截止日、新品公式、参照款筛选、取整规则、部分留空的交付策略；检查分类和五平台去年数据是否可用。
2. **新品本地试算**：针对当前新品模板，先支持明确指定参照款，输出完整计算明细；规则与商品映射放在外部配置中。
3. **核对试算**：核对数仓原始数量、日期、整款 SKU 范围及分配合计；用人工最终需求对比，记录差异原因。人工结果是业务参考，不直接等同于预测准确率。
4. **接入预测填充**：沿用既有列定位、空值保护、公式保护、版本检查及写后回读；验证成功、异常留空、失败降级、重试和强制重搬。
5. **扩展能力**：规则明确后接入自动参照选择，再完善老款历史窗口与表格支持。实际销售周期结束后，另行评估预测与实际发货的偏差。

文档整理阶段不启用预测写入。现阶段最先要解决的是准确周期、虚拟分类及去年历史来源，而不是直接给现有近30天销量乘固定倍数。
