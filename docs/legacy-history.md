# 老品历史数据支持与运营确认清单

## 支持范围

历史填充开关 `FILL_HISTORY_ENABLED` 控制新品及老品的近30天销量填充。款式分类沿用 `config/sheet-layout.toml`；五个平台独立统计，日期为预估日前30个完整自然日，使用发货口径。

- 表格已有五个平台近30天列时，核对商品与来源后填入空白销量单元格。
- 只有需求列、或部分平台缺少近30天列时，在对应需求列前补齐销量列。
- 老品已有往年区间、实发减实退的表头和内容保留；没有这些字段时不生成历史字段，不设置历史日期。
- 往年区间文字或不同历史指标的区间差异不参与本次近30天计算，也不据此修改原列。
- 历史销量原值相同则跳过，不同则保留并返回待核对；需求数量、公式、合计、其他部门内容保持保护。
- 平台不明确、重复列、新老品混合、需要移动原有列等情况继续阻止写入。

结构预览命令仍可展示完整的老品历史字段建议；实际补列命令及自动填充只补近30天列。往年区间配置仅用于完整结构预览，不决定此次查询日期。

| [绒趣小动物套头帽](https://kocotree.feishu.cn/sheets/E6L4sD0hvh9CURtCb3kcpwrKnFh) | 1 / 18 | 唯品、拼多多、猫超为25.9.9—12月；POP为25.9—12月；自营为25.9—26.2月 |

| [啵啵软糖雨靴](https://kocotree.feishu.cn/sheets/JCgTseA6ahIGjGt1mkAcXdbtnFe) | 1 / 21 | 唯品、拼多多、猫超、POP为25.9—10月；自营为25.9—26.3月 |

表头记录说明历史周期随任务、款式及平台变化，不能根据款号或季节自动决定。需求商品行是数值，无法据此还原运营的完整计算公式；雨靴 POP 有两项为15件，人工最终结果不全为整十。

部分样本的表外需求汇总公式引用整段列范围，可能包含历史参考列。项目保留原公式，不将此类公式作为预测算法或自行调整。市场部之外汇总口径需由业务核对。

## 数仓只读核查结果

以下为2026年9月15日读取时的观察结果，不代表每个 SKU 或每一天的数据都完整。

### 四个平台出库明细

来源为 `dwd_whs_outstock_detail_f`，使用销售出库、已出库单据和出库状态；平台范围沿用 `config/sales-sources.toml`。

| 平台 | 最早观察发货日期 | 最晚观察发货日期 | 有记录的日期数 |
| --- | --- | --- | ---: |
| 唯品会 | 2024-01-01 | 2026-09-12 | 974 |
| 拼多多 | 2024-01-01 | 2026-09-12 | 981 |
| 京东 POP | 2024-01-01 | 2026-09-12 | 980 |
| 天猫超市 | 2024-01-01 | 2026-09-12 | 980 |

技术上可以查询指定时间范围，但起止日期须由运营提供；还需针对具体窗口逐日核验并区分停销、零发货与同步缺口。这些统计不应直接作为历史填充通过的证据。

### 京东自营历史出库候选

来源 `bwd_rpa_jd_inventory_product_detail` 除 `outbound_30d` 外，还包含 `outbound_yesterday`，以及商品条码、店铺、快照日期等字段。

核查现有自营店铺范围：

- 快照从2023-02-08到2026-09-11，共1312个日期。
- 针对人工样本涉及的历史跨度，查询 `[2025-09-01, 2026-04-01)`，观察到212个快照日期、1,732,127行记录，`outbound_yesterday` 无空值。

因此存在用日出库字段统计长周期的候选路径。正式实现前仍需核实 `dt` 与“昨日”的业务日期对应关系、同日同条码多行的维度和去重，以及每个 SKU 的日覆盖。当前没有将该候选接入生产统计。滚动30天字段不能逐日累加。

### 拼多多实退候选

候选表：

- `dwd_trd_sys_aftersale_order_detail_f`：系统售后明细，包含聚水潭标准 API 与奇门 API 等来源。
- `std_api_jstbz_trd_sys_aftersale_order_detail_f`：标准 API 系统售后明细。
- `std_api_pdd_trd_aftersale_order_detail_f`：拼多多平台售后明细，可供后续交叉核验。

系统售后明细已确认存在以下字段：

| 用途 | 字段 |
| --- | --- |
| 时间候选 | `return_time`、`refund_time`、`confirm_date`、`create_time` |
| 数量候选 | `aftersale_num`、`apply_aftersale_num` |
| 类型与状态 | `aftersale_type`、`aftersale_status`、`aftersale_order_status`、`product_status` |
| 关联 | 售后主子单号、销售主子单号、来源销售主子单号、`spec_code` |
| 来源与平台 | `data_source`、`company`、`channel`、`shop_code`、`shop_name`、`dept_name` |

已观察到 `channel=拼多多` 的记录；仅用 `dept_name=拼多多` 查询没有返回记录，标准层部分记录的部门为空。出库表的部门筛选不能直接套到售后表，应核实渠道、店铺与现有出库平台范围的对应关系。

售后类型包含普通退货、仅退款、拒收、换货、补发等；状态含已确认、待确认、作废等。部分仅退款或作废记录也有 `return_time`，因此有退货时间不等于实际收货，申请数量也不等于实退数量。

正式计算前需要确认实际收货标准、统计时间、换货与拒收是否计入、跨周期退货如何归属，并检查 API 来源重叠、售后单去重和与原出库的关联。当前未计算或填写“实发－实退”。

## 验证记录

- 三份人工老品样本57个 SKU 全部通过商品身份核对，五个平台共285项近30天数据检查除目标非空外无其他阻塞项。检查日采用已授权的2026-09-12，观察窗口为2026-08-13至2026-09-11。
- 在[套头帽测试副本](https://kocotree.feishu.cn/sheets/YBImsqoDEhUh4xttEBocnx5HnLc)上准备空白近30天商品格，真实填写18个 SKU、90项销量。原始人工样本未修改。
- 回读核对往年数据、需求数量、公式、样式和合并范围；同日期重复执行没有销量写入。
- 自动化测试覆盖老品已有完整历史列、缺近30天列、无历史日期的初始模板，以及完整历史填充流程。

本地证据位于 `artifacts/legacy-manual-review/`、`artifacts/legacy-source-review/`、`artifacts/legacy-live/`，这些运行产物不提交 Git。

## 提供给运营的确认清单

按“本次下单任务＋款式＋平台”记录以下信息；本项目不代填业务决定。

| 项目 | 需要运营明确的内容 |
| --- | --- |
| 历史参考区间 | 起止日期；同款不同平台是否分别设置；月份简写的准确日期 |
| 预测周期 | 本次预估日、需求截止日 |
| 预测规则 | 各平台新老款的公式、参照款及调整系数 |
| 取整与分配 | 款式和SKU取整单位、方向、差额分配及人工例外 |
| 拼多多实退 | 实际收货标准、使用日期、仅退款/拒收/换货处理、跨期归属 |
| 部分完成 | 个别平台或SKU无法填充时，是否允许交付已填部分 |

规则以明确配置或任务参数落地后，再实现对应历史区间和预测计算。近30天填充可以独立使用。
