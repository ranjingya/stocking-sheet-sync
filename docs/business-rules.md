# 业务规则

## 处理范围

只处理市场部五个平台：京东自营、京东POP、拼多多、唯品会、天猫超市。需求表商品行确定查询SKU范围；表外SKU不参与同款汇总、同比、分配和兜底阈值计算。

以SKU精确匹配商品主数据，核对款号、名称、规格。查不到、身份不一致、同SKU多款或重复冲突进入人工核验。

新品年份由 `sheet.layout.new_year` 配置。新品支持近30天；老品支持近30天和公式预测。混合分类或未知分类不自动填充。

## 日期与来源

自动填充以原始备份创建时的上海日期为基准，近30天为该日前30个完整自然日。例如9月21日对应8月22日至9月20日。重试沿用同批次日期，不从表格名称推断日期，不因数仓缺数据自动向前挪动窗口。

| 数据 | 来源及条件 |
| --- | --- |
| 商品主数据、季节标签 | `std_api_jstbz_product_spec_info_f`，聚水潭标准API、公司 |
| 京东自营近30天、去年同期近30天 | 源 MySQL 的 `jd_inventory_product_detail`，分别读取基准日前一日和去年对应日期的 `outbound_30d` |
| 拼多多近30天、去年同期近30天 | `ads_whs_outstock_pdd_base_sku_window`，分别读取 `sales_out_qty_30d`、`ly_sales_out_qty_30d` |
| 唯品会近30天、去年同期近30天 | `ads_whs_outstock_wp_base_sku_window`，字段同拼多多 |
| 京东自营特殊历史区间 | 源 MySQL 的 `jd_inventory_product_detail`，配置的自营店铺 |
| 拼多多、唯品会特殊历史区间及POP、猫超全部区间 | `dwd_whs_outstock_detail_f`，销售出库且单据/出库状态已出库 |
| POP与猫超 | 市场部其他部门下，通过配置的店铺ID区分 |
| 全公司占比 | 使用基准日前30个完整自然日销量；ADS公司分组近30天汇总 + MySQL京东自营近30天汇总 |

拼多多和唯品会的 ADS 按 SKU 匹配，查询基准日前一天的 `stat_date`；去年同期指标也读取这个快照上的去年同期字段。原值为0时按0读取。若目标快照日整天无记录或缺少所需SKU，使用 `dwd_whs_outstock_detail_f` 按相应30天区间统计，并在通知中标明来源；明细数据仍需通过出库日期覆盖及去重校验。ADS已有有效值保持不变，仅对缺失SKU查询明细；明细覆盖正常且无该SKU出库记录时记0。ADS记录重复或数值无效时交由人工核对。

京东自营按 `barcode` 和配置的店铺查询源 MySQL；7/14/28/30/60/90天使用截止日现成滚动字段，其他长度累加 `outbound_yesterday`，要求逐SKU日覆盖完整。`dt` 日期偏移由配置指定，当前为0。

明细按发货/出库时间查询，按来源、公司、出库单、明细和SKU去重。来源正常且无该SKU记录时可记零；平台日期缺失、重复冲突不能当零。拼多多和唯品会的两个30天指标使用ADS。

老款预测的去年后续周期来源不可用时，可使用需求表内已填的完整历史数量，并核对表头起止日期及全部SKU。近30天和去年同期近30天列没有日期证据，来源不可用时留待核对；来源正常时，表内相同数值可直接复用。

## 老品需求周期

- 夏款：当年8月31日。
- 秋冬款：尚未经过当年1月31日则取该日，否则取次年1月31日。
- 四季、无季节标签：取不早于基准日的最近一个1月31日或8月31日。
- 标签冲突需核验。跨季夏款不自动延长一年。

去年同期近30天：以去年同日为基准向前取30天。闰年2月29日映射到去年2月28日。

去年后续周期：去年基准日到去年对应的需求截止日，包含首尾。例如基准日2026年9月4日、截止日2027年1月31日，历史周期为2025年9月4日至2026年1月31日。

## 全公司出库自动补充

老款开启历史填充或预测时，优先使用表内带日期且与基准日近30天窗口一致的完整全公司销量。表内缺少该数据或存在空缺，且至少一款的全部需求SKU全公司出库均可用时，在市场部分组最前面补充一列，标题如 `全公司近30天出库 26.8.29-26.9.27`，按需求表中的SKU填数量，供公司占比兜底使用。全公司出库按款填写：某款任一需求SKU缺失时整款留空，所有款均不完整时不新增列，已有列保留；有效的0值属于可填数量。新品只处理近30天历史。

```text
SKU全公司近30天出库 = ADS的sales_out_qty_30d + MySQL京东自营的outbound_30d
```

- 周期为基准日前30个完整自然日，不含基准日；所有款式使用同一窗口，与季节无关。例如2026年10月6日统计2026年9月6日至10月5日。表内数量必须有匹配的日期标题才可复用。
- 公司部分：`ads_whs_outstock_gs_base_sku_window` 按 `spec_code` 匹配SKU，读取基准日前一天 `stat_date` 快照的 `sales_out_qty_30d`。该表为公司分组汇总，不含京东自营终端出库。
- 京东部分：`jd_inventory_product_detail` 按 `barcode` 和配置的自营店铺读取；读取基准日前一天快照的 `outbound_30d`，限定配置的自营店铺。
- 指定日期周期：公司部分使用 `dwd_whs_outstock_detail_f` 的 `spec_code`、`shop_id`、`outstock_time`、`outstock_num`，按店铺“销售出库分组-全公司＝公司”筛选，限定销售出库且单据与出库状态已出库，按业务明细去重求和；京东部分累计对应日期的 `outbound_yesterday`。显式周期查询即使恰好30天也按明细统计；预测兜底的近30天查询使用ADS与京东滚动值。
- 来源表及字段位于 `config/rules.toml` 的 `company_sales.summary`；京东复用 `jd_platform` 指定的MySQL配置。ADS缺记录、重复或数量无效时留空，0值有效。
- 表内生命周期列及无日期的人工列保持原内容；全公司近30天使用独立带日期的列。自动列同周期完整时复用，有空缺则补齐，普通模式下数值不同的SKU跳过。
- 自动列日期不一致时标明原因并保留原列；强制覆盖时，须新周期所有SKU均可用才更换日期及数量。商品行公式始终保留。
- 任一来源缺失、重复或数量无效时，该款所有需求SKU公司数量留空，通知原因以“全公司：”说明。数据完整的其他款、各平台历史及不依赖公司占比的预测正常处理；需要公司占比的款式须全部需求SKU公司数量有效且合计大于零。

## 公式与分配

同款同平台：

```text
同比倍率 = 今年近30天 / 去年同期近30天
使用倍率 = min(同比倍率, 配置倍率上限)
理论总需求 = 去年后续周期销量 × 使用倍率
```

SKU默认按该平台今年近30天销量占比分配理论总需求。不是对每个SKU分别计算同比。

仅当表内同款SKU少于10个且该平台近30天总销量少于20件时，使用全公司相同近30天窗口的销量占比分配。该比例只影响SKU分配，不改变理论总需求。公司数据缺失、歧义、不完整或总和为零时预估留空。

去年同期近30天同款同平台合计少于20件时，历史数据照常填充，预估留空并标记“去年同期30天基数过低”。阈值由 `config/rules.toml` 的 `forecast.previous_sales_below` 指定。倍率上限由同文件的 `forecast.growth_multiplier_cap` 指定，默认1.5，必须为大于等于1的有限数值。下降倍率不设下限，触及上限不增加表格或通知说明。

理论总需求按SKU占比分配后，每个SKU直接四舍五入到10的倍数（ROUND_HALF_UP），例如14→10、15→20、25→30。取整单位由 `config/rules.toml` 的 `forecast.rounding_unit` 指定，默认10。最终款式合计为各SKU取整数量之和，不进行差额回补。

不扣减库存或在途，不纳入拼多多退货专项规则。程序计算后写整数，预估单元格不写动态公式。

## 表格保护与表头

保留人工需求、其他部门内容与人工历史列。需求汇总使用各平台人工需求栏的逐列 SUM 公式，排除历史销量和预估栏；其他原公式保留。历史或预估目标值相同则复用；不同数值或商品行已有公式时停止覆盖。

表头示例：`唯品近30天`、`唯品去年同期近30天`、`唯品25.9.4-26.1.31`、`预估-唯品会`。日期表头包含首尾日期。同表多款截止日不同时列出实际区间。

能通过同列公式或其他列唯一确认完整商品合计行时，补齐空白的市场部需求及历史合计公式；原合计公式保留，由飞书在插列时调整引用。内容、公式、样式和布局按快照校验。

需求汇总列由 `matching.summary_headers` 定位；人工需求栏按市场部各平台 `demand_headers` 及 `matching.other_demand_headers` 匹配最底层标题。每个商品行仅合计这些栏，人工值与样式保持原样。写入前核对版本和原公式，回读后核对汇总结果；已有正确公式重复执行不写入。

## 填充结果与通知

历史填充与预测分别判断结果。历史输入有效且目标没有冲突时正常填入；预测因低基数、公司占比不可用或销量占比合计为零而无法计算时，仅跳过预测单元格。历史来源或目标历史存在冲突时，该平台预测也需要等待历史核对；各平台之间独立处理。预测合计单元格冲突只阻断预测写入。

通知分别显示历史、预测完成状态，原因按平台列出；多款时附款号。原因包括开关关闭、新品预测暂不支持、历史快照缺失、日期覆盖不完整、SKU缺失或重复、数量无效、来源读取失败、表内历史缺少日期依据、历史数值冲突、预测低基数、公司占比不可用、平台占比为零、预测已有不同内容，以及商品识别、表格识别、写入核验和交付失败。来源问题携带可用的日期与SKU，目标冲突携带单元格位置。

使用ADS整天或SKU无数据的DWD兜底时标记“ADS 表周期或SKU无数据，使用 DWD 明细表填充”。正常完成不另写原因；具体错误在通知与日志中使用相同的中文说明。

## 手动补充

`fill` 按款号、平台识别首次填充、补历史、补预估和已完整状态。所需数据已完整时直接保留；待补范围的已有历史与来源核对，冲突仅隔离同款同平台。新增SKU参与所在款全部需求SKU的计算，写入仅覆盖空白；强制覆盖参数允许重填已有数字，原公式和人工需求保留。已填后续周期列的日期与基准日不符时保留原标题，相关待补款平台提示核对日期。

自动填充和手动fill的历史数量按“款号＋平台＋历史指标”判断可用性：某款去年后续周期不可用时，今年近30天、去年同期及其他款可用数据正常填入；预测单独校验所需输入。表内历史冲突保留该款该平台对应指标，其他周期正常填写；存在历史冲突时不写入该款该平台预测。
