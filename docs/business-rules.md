# 业务规则

## 处理范围

只处理市场部五个平台：京东自营、京东POP、拼多多、唯品会、天猫超市。需求表商品行确定查询SKU范围；表外SKU不参与同款汇总、同比、分配和兜底阈值计算。

以SKU精确匹配商品主数据，核对款号、名称、规格。查不到、身份不一致、同SKU多款或重复冲突进入人工核验。

新品年份由 `sheet.layout.new_year` 配置。新品支持近30天；老品支持近30天和公式预测。混合分类或未知分类不自动填充。

## 日期与来源

自动填充以原始备份创建时的上海日期为基准，近30天为该日前30个完整自然日。例如9月21日对应8月22日至9月20日。重试沿用同批次日期，不从表格名称推断日期，不因数仓缺数据自动向前挪动窗口。

| 数据 | 来源及条件 |
| --- | --- |
| 商品主数据、季节标签 | `std_api_jstbz_product_spec_info_f`，聚水潭标准API、公司 |
| 京东自营近30天、去年同期近30天 | 源 MySQL 的 `jd_inventory_product_detail`，分别读取基准日前一日和去年对应日期的 `outbound_30d` |
| 拼多多近30天、去年同期近30天 | `ads_whs_outstock_pdd_base_sku_window`，分别读取 `sales_out_qty_30d`、`ly_sales_out_qty_30d` |
| 唯品会近30天、去年同期近30天 | `ads_whs_outstock_wp_base_sku_window`，字段同拼多多 |
| 京东自营特殊历史区间 | 源 MySQL 的 `jd_inventory_product_detail`，配置的自营店铺 |
| 拼多多、唯品会特殊历史区间及POP、猫超全部区间 | `dwd_whs_outstock_detail_f`，销售出库且单据/出库状态已出库 |
| POP与猫超 | 市场部其他部门下，通过配置的店铺ID区分 |
| 全公司占比 | 优先使用表内去年生命周期销量；缺失时取DWD公司分组出库 + MySQL京东自营出库 |

拼多多和唯品会的 ADS 按 SKU 匹配，查询基准日前一天的 `stat_date`；去年同期指标也读取这个快照上的去年同期字段。原值为0时按0读取。若目标快照日整天无记录，使用 `dwd_whs_outstock_detail_f` 按相应30天区间统计，并在通知中标明来源；明细数据仍需通过出库日期覆盖及去重校验。ADS 当天有数据但缺少所需 SKU、记录重复或数值无效时，不切换来源，交由人工核对。

京东自营按 `barcode` 和配置的店铺查询源 MySQL；7/14/28/30/60/90天使用截止日现成滚动字段，其他长度累加 `outbound_yesterday`，要求逐SKU日覆盖完整。`dt` 日期偏移由配置指定，当前为0。

明细按发货/出库时间查询，按来源、公司、出库单、明细和SKU去重。来源正常且无该SKU记录时可记零；平台日期缺失、重复冲突不能当零。拼多多和唯品会的两个30天指标使用ADS。

老款预测的去年后续周期来源不可用时，可使用需求表内已填的完整历史数量，并核对表头起止日期及全部SKU。近30天和去年同期近30天列没有日期证据，来源不可用时留待核对；来源正常时，表内相同数值可直接复用。

## 老品需求周期

- 夏款：当年8月31日。
- 秋冬款：尚未经过当年1月31日则取该日，否则取次年1月31日。
- 四季、无季节标签：取不早于基准日的最近一个1月31日或8月31日。
- 标签冲突需核验。跨季夏款不自动延长一年。

去年同期近30天：以去年同日为基准向前取30天。闰年2月29日映射到去年2月28日。

去年后续周期：去年基准日到去年对应的需求截止日，包含首尾。例如基准日2026年9月4日、截止日2027年1月31日，历史周期为2025年9月4日至2026年1月31日。

## 全公司出库自动补充

老款开启历史填充或预测时，优先使用表内完整的全公司去年生命周期销量。表内缺少该数据或存在空缺时，在市场部分组最前面补充一列，标题如 `全公司出库 25.9.28-26.1.31`，按需求表中的SKU填数量，供公司占比兜底使用。新品只处理近30天历史。

```text
SKU全公司出库 = DWD中该SKU属于“公司”分组的销售出库 + MySQL中该SKU的京东自营终端出库
```

- 周期沿用本次“去年后续周期”，包含首尾日期；同表不同款季节截止日不同，按各款分别查询，标题列出全部区间。
- 公司部分：`dwd_whs_outstock_detail_f` 按 `spec_code` 匹配SKU，按 `shop_id` 关联店铺信息表的“聚水潭店铺编码”，仅统计“销售出库分组-全公司”为“公司”的明细。“不计入”、未匹配、空白或冲突分组均不属于明确的“公司”分组，不纳入公司出库，并保留排除明细。筛选公司、销售出库、单据及出库状态已出库，并按业务明细去重。
- 京东部分：`jd_inventory_product_detail` 按 `barcode` 和配置的自营店铺读取；固定周期用滚动值，其余周期累加日出库。
- 店铺来源、字段与分组口径位于 `config/rules.toml` 的 `company_sales`；程序通过现有飞书数据应用的服务端接口读取分组表，应用需有该多维表读取权限。
- 表内完整人工列保留并优先使用；人工列不完整时补独立自动列，不混合两个周期的数据。自动列同周期完整时复用，有空缺则补齐，普通模式下数值不同的SKU跳过。
- 自动列日期不一致时标明原因并保留原列；强制覆盖时，须新周期所有SKU均可用才更换日期及数量。商品行公式始终保留。
- 任一来源缺失、重复或数量无效时，该SKU公司数量留空，通知原因以“全公司：”说明。有效的其他SKU、各平台历史及不依赖公司占比的预测正常处理；需要公司占比的款式须全部需求SKU公司数量有效且合计大于零。

## 公式与分配

同款同平台：

```text
同比增长率 = (今年近30天 - 去年同期近30天) / 去年同期近30天
理论总需求 = 去年后续周期销量 × 今年近30天 / 去年同期近30天
```

SKU默认按该平台今年近30天销量占比分配理论总需求。不是对每个SKU分别计算同比。

仅当表内同款SKU少于10个且该平台近30天总销量少于20件时，使用全公司销量占比分配。该比例只影响SKU分配，不改变理论总需求。公司数据缺失、歧义、不完整或总和为零时预估留空。

去年同期近30天同款同平台合计少于20件时，历史数据照常填充，预估留空并标记“去年同期30天基数过低”。阈值由 `config/rules.toml` 的 `forecast.previous_sales_below` 指定。其余情况不设同比增长率上限。

理论总需求按SKU占比分配后，每个SKU直接四舍五入到10的倍数（ROUND_HALF_UP），例如14→10、15→20、25→30。取整单位由 `config/rules.toml` 的 `forecast.rounding_unit` 指定，默认10。最终款式合计为各SKU取整数量之和，不进行差额回补。

不扣减库存或在途，不纳入拼多多退货专项规则。程序计算后写整数，预估单元格不写动态公式。

## 表格保护与表头

保留人工需求、其他部门内容、原公式与人工历史列。已有目标值相同则复用；不同数值或商品行已有公式时停止覆盖。

表头示例：`唯品近30天`、`唯品去年同期近30天`、`唯品25.9.4-26.1.31`、`预估-唯品会`。日期表头包含首尾日期。同表多款截止日不同时列出实际区间。

能通过同列公式或其他列唯一确认完整商品合计行时，补齐空白的市场部需求及历史合计公式；原合计公式保留，由飞书在插列时调整引用。内容、公式、样式和布局按快照校验。

## 填充结果与通知

历史填充与预测分别判断结果。历史输入有效且目标没有冲突时正常填入；预测因低基数、公司占比不可用或销量占比合计为零而无法计算时，仅跳过预测单元格。历史来源或目标历史存在冲突时，该平台预测也需要等待历史核对；各平台之间独立处理。预测合计单元格冲突只阻断预测写入。

通知分别显示历史、预测完成状态，原因按平台列出；多款时附款号。原因包括开关关闭、新品预测暂不支持、历史快照缺失、日期覆盖不完整、SKU缺失或重复、数量无效、来源读取失败、表内历史缺少日期依据、历史数值冲突、预测低基数、公司占比不可用、平台占比为零、预测已有不同内容，以及商品识别、表格识别、写入核验和交付失败。来源问题携带可用的日期与SKU，目标冲突携带单元格位置。

使用ADS整天无数据的DWD兜底时标记“ADS 表周期无数据，使用 DWD 明细表填充”。正常完成不另写原因；具体错误在通知与日志中使用相同的中文说明。
